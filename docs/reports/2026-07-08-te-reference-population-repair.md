# TE Reference Population Artifact-Integrity Repair

**Date:** 2026-07-08
**Issue:** [#257](https://github.com/Prometheus-Frameworks/TIBER-Rookies/issues/257)
**Follow-up to:** [#255](https://github.com/Prometheus-Frameworks/TIBER-Rookies/issues/255) /
`docs/reports/2026-07-08-machine-readable-artifact-audit.md`

## Scope

This is an artifact-integrity repair, not a Forecast issue. No Forecast files were touched, no
new rookie evaluation logic was introduced, no schemas were redesigned beyond what the repair
required, and no new capability artifacts were created.

## Answers to the audit questions

### 1. Do the TE reference-population files actually contain TE populations?

No. Verified across all five files
(`data/historical/te_reference_populations/{2017-2021}_te_receiving_population.json`).

### 2. If not, what do they contain?

Each file was byte-for-byte identical to the first N alphabetically-sorted rows (by
`player_name`) of that same season's real
`data/historical/wr_reference_populations/{year}_wr_receiving_population.json`, with only the
`"position"` field changed from `"WR"` to `"TE"`. Confirmed programmatically: for all five
seasons, every field except `position` matched a same-named row in the corresponding WR file
exactly (`receptions`, `receiving_yards`, `receiving_tds`, `source_name`, `source_url` all
identical). "A.J. Brown" — a wide receiver — was row 1 of the 2017 "TE" file with his real WR
stats and `"position": "TE"`.

### 3. Does a correct TE reference population already exist elsewhere in the repo?

No. Checked:
- Every other data directory in the repo (`data/historical/`, `data/processed/`, including
  `te_production_profiles/`, which holds only two individual hand-curated career profiles —
  not a cohort/season population usable for z-score normalization).
- Two candidate unmerged branches whose names suggested a TE-lane fix
  (`chore/regenerate-comps-post-pr75-v2`, `chore/regenerate-comps-artifact`): the first branch
  carries the identical bug (same mislabeled WR data); the second predates the TE lane entirely.
- No cached CFBD API responses exist anywhere in the repo.

### 4. Is this a generation bug, labeling bug, or historical copy error?

A **fabrication/authoring error present from the moment the TE historical-comps lane was
introduced** — not a later regression. The commit that first added the TE lane
("Add TE historical comps lane and reference populations") added the mislabeled files directly;
they were never correct. `scripts/fetch_te_reference_populations.py` — the script whose job is
to populate this directory — is implemented correctly (queries CFBD's
`stats/player/season?category=receiving` and filters to `TE`/`H-BACK`/`FB` positions), but the
committed files were not produced by running it. No downstream validation ever checked that the
content was genuinely TE data — the loader only validates field presence and that `position` is
one of `TE`/`H-BACK`/`FB`, which a relabeled WR row satisfies trivially.

### 5. Which downstream files, reports, or docs depend on these artifacts?

- `scripts/compute_historical_comps.py` loads this directory (`_load_te_reference_populations`)
  and uses it to z-score-normalize TE historical rows' `production_0_100`.
- Because the corrupted files had 45 rows each (above the 30-row minimum), they were treated as
  a "valid" reference population, which caused
  `exports/promoted/historical-comps/2026_historical_comps_v0.json` to set
  `methodology_compatibility_by_position.TE: true` and
  `similarity_quality_by_position.TE.status: "ui_safe"` — i.e. **the promoted export was
  actively claiming TE comps were safe for UI display on the strength of relabeled WR data.**
  (Confirmed by inspecting the committed export before this fix.)
- `docs/historical-comps-contract.md` never documented the TE reference-population mechanism at
  all (a pre-existing omission, not introduced by this fix).
- `docs/reports/2026-07-08-machine-readable-artifact-audit.md` (issue #255) flagged this as an
  `unknown_requires_followup` item.

## Root cause (summary)

Fabrication at authoring time: TE reference-population files were seeded with relabeled WR rows
instead of being generated by the (correctly implemented) fetch script, and no test or validator
existed to catch that the content wasn't genuinely TE data.

## Repair performed

Repair via regeneration was attempted but is not currently possible: outbound requests to
`https://api.collegefootballdata.com` reach the API (confirmed via direct request) but return
`401 Unauthorized` without a `CFBD_API_KEY`, and none is configured in this environment.
Fabricating placeholder TE numbers to fill the gap would repeat the exact mistake this issue
exists to fix, so the artifacts are **quarantined** rather than repaired with unverifiable data:

1. All five `data/historical/te_reference_populations/{year}_te_receiving_population.json` files
   were replaced with `[]`.
2. Added `data/historical/te_reference_populations/README.md` documenting the quarantine, root
   cause, effect on downstream normalization, and exact regeneration command for when a
   `CFBD_API_KEY` is available.
3. Added `tests/test_te_reference_population_integrity.py`:
   - asserts each file is a valid JSON array;
   - **regression guard** — asserts no TE row's `(player_name, receptions, receiving_yards,
     receiving_tds)` tuple matches a row in that year's WR reference population (this test would
     have caught the original defect and fails if it recurs);
   - asserts the files are currently empty (documents the quarantine state; must be deliberately
     updated, not silently overwritten, once real data lands).
4. Updated `tests/test_compute_historical_comps.py::test_te_reference_population_file_enables_population_scope`
   to exercise the positive path (population scope enabling) against a synthetic temp-directory
   fixture instead of the real (now-quarantined) files, matching the existing pattern already
   used for the equivalent WR test. Added
   `test_te_reference_population_currently_quarantined_yields_no_valid_population` to assert the
   real directory now correctly yields no valid population.
5. Updated `docs/historical-comps-contract.md` with a "Historical TE reference population
   infrastructure" section (parallel to the existing WR section, which this contract previously
   lacked entirely) documenting the quarantine and its effect on `methodology_compatible`/
   `ui_safe` status, plus a note under "Local population posture" flagging that the currently
   committed `exports/promoted/historical-comps/2026_historical_comps_v0.json` predates this fix.

Full test suite (`pytest`, 380 tests) passes after these changes.

## Downstream impact recorded

- **`exports/promoted/historical-comps/2026_historical_comps_v0.json` was NOT regenerated in
  this PR.** Attempting to regenerate it surfaced a separate, pre-existing staleness problem
  unrelated to this issue: the committed artifact was last generated before roughly nine
  subsequent commits of rookie-alpha predraft changes (evidence-summary policy edits, CFBD
  production backfills, an RB SPORQ blend change, etc.) — regenerating today would also change
  unrelated WR/TE rookie counts and coverage numbers that have nothing to do with the TE
  mislabeling defect. Per this issue's hard boundary ("do not broaden into unrelated audit
  findings"), that regeneration is left as follow-up rather than bundled here. Documented in
  `docs/historical-comps-contract.md`. **Concretely, this means the currently-committed export
  still contains the pre-fix `methodology_compatibility_by_position.TE: true` /
  `similarity_quality_by_position.TE.status: "ui_safe"` values** until it is next regenerated —
  at which point the quarantined (empty) reference population will automatically produce the
  correct, conservative non-`ui_safe` result with no further code changes needed.
- No other files were found to depend on `te_reference_populations/` beyond what's listed above.

## Proposed bounded follow-up

- Regenerate `exports/promoted/historical-comps/2026_historical_comps_v0.json` against current
  rookie-alpha data (separate issue — this also resolves the pre-existing staleness noted above
  and will pick up the corrected TE non-compatible status as a side effect).
- Once a `CFBD_API_KEY` is available, run
  `python3 scripts/fetch_te_reference_populations.py --years 2017 2018 2019 2020 2021` to
  populate real TE data, then update the two tests in
  `tests/test_te_reference_population_integrity.py` that currently assert the quarantine state.

## Decision

```text
te_reference_population_artifacts_quarantined
```

This confirms only that the TE reference-population integrity issue has been investigated,
root-caused, and quarantined. It does not authorize Forecast consumption of any Rookies artifact.
